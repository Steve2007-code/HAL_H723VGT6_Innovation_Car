## 1. P0-1：`Nav_Update()` 在非 `NAV_RUN` 状态仍输出角速度 ★最严重

### 1.1 证据（`MDK-ARM/USER/src/Nav.c:253~262`）

```c
    /* ---- 航向环: 目标 = 当前段方向 ---- */
    yaw_err = Attitude_WrapPi(s_yaw_t - g_pose.yaw);
    wz = s_kp_yaw * yaw_err - s_kd_yaw * g_att.yaw_rate;

    if (g_nav_state != NAV_RUN || s_wpn == 0)
    {
        if (fabsf(yaw_err) < 0.035f) wz = 0.0f;     /* 只挡 2 度以内 */
        Chassis_SetBodyVel(0.0f, 0.0f, wz);          /* ★ 仍然输出 wz */
        return;
    }
```

这段对所有**非 `NAV_RUN`** 的状态都生效：`NAV_IDLE` / `NAV_DONE` / `NAV_FAIL`。

### 1.2 为什么会导致「走完一直旋转」

1. `z 4 0` 走到终点 → `s_wp_next()` → `s_wpn = 0`、`g_nav_state = NAV_DONE`、`Chassis_Hold()`（只清一次）；
2. 之后**每 5ms** 都走上面那个分支：`s_yaw_t` 仍保留**最后一段的航向**，实际 `g_pose.yaw` 只要差超过 2°，就持续输出 `wz`；
3. `g_pose.yaw = WrapPi(g_att.yaw + s_yaw_off)`，而 `g_att.yaw` 是陀螺积分，**存在零偏漂移**；
4. 更关键：`Attitude.c:99` 的在线零偏修正条件是

```c
if (g_nav_state == NAV_IDLE && fabsf(...) < 0.03f)
    g_att.gz_bias += ...;
```

**只在 `NAV_IDLE` 生效，`NAV_DONE` 不修正** → 走完停在 `NAV_DONE` 时零偏永远学不正 → yaw 持续漂移 → 航向环持续输出 `wz` → **车一直转**。

### 1.3 为什么还会导致「不发命令车自己动」

- 手动 `<<v ...>>` 会把状态置 `NAV_MANUAL`，800ms 无刷新后（`Nav.c:230~236`）自动退回 `NAV_IDLE`；
- 一进 `NAV_IDLE`，同一个分支立刻用 `s_yaw_t` 做航向保持 → **车自己转头**；
- 同理 `x` 急停只是 `Nav_Stop()` 置 `NAV_IDLE` + `Chassis_Hold()`，**下一个 5ms 就又开始输出 `wz`** → 急停形同虚设。

> 你之前怀疑是「串口干扰」，其实**真正的来源是导航层自己在动**。这也能解释为什么静止 `o` 打印里 yaw 会从 90 漂到 88.14 之后还在缓慢变化。

### 1.4 建议修法（`Nav.c`，把航向环挪进 `NAV_RUN` 分支）

```c
    /* ---- 非运行态: 一律硬停, 不做航向保持 ---- */
    if (g_nav_state != NAV_RUN || s_wpn == 0)
    {
        Chassis_Hold();
        return;
    }

    /* ---- 航向环: 目标 = 当前段方向 (只在实际运行段工作) ---- */
    yaw_err = Attitude_WrapPi(s_yaw_t - g_pose.yaw);
    wz = s_kp_yaw * yaw_err - s_kd_yaw * g_att.yaw_rate;

    /* ---- 拐点: 段航向未对准先原地转向, 不平移 ---- */
    if (fabsf(yaw_err) > NAV_TURN_GATE)
    {
        Chassis_SetBodyVel(0.0f, 0.0f, wz);
        return;
    }
```

要点：把 `yaw_err / wz` 的计算**移到判断之后**，避免「已赋值未使用」的警告。

**副作用**：失去「静止时自动保持朝向」的能力。这是好事——上电时车被碰歪不会自己回正，急停真能停住。若将来确实要姿态保持，应单独做一个显式命令，并加「偏差 > 30° 视为漂移不修正」的保护。

## 2. P0-2：`K,1` 不清 `s_yaw_ack`（F103 侧，上一轮已提，仍未修）

`mcu_link.c:157~162` 目前只有 `if (s_k_code == LINK_K_ENABLED) s_yaw_ack = 1;`，**没有任何清 0 路径**。

H723 中途重启 → `Link_Init()` 重跑 → `s_yaw_enabled = 0` + 发 `K,1`；F103 因持续收 `A` 帧而 `link_lost=0`，但 `s_yaw_ack` 仍为 1 → **永不补发 `E,1`** → yaw 永久失能，且 `A`/`Y` 双向正常、零提示。

**修法（1 行）**：

```c
if (s_k_code == LINK_K_READY) s_yaw_ack = 0;   /* K,1 = H723 刚上电, 使能状态已丢 */
```

## 3. P0-3：UART7 优先级与 FIFO 配置

| 项 | 实测 | 问题 |
|---|---|---|
| `stm32h7xx_hal_msp.c:451` | `HAL_NVIC_SetPriority(UART7_IRQn, 0, 0)` | 与 `TIM4`（L356 也是 `(0,0)`）**同级** |
| `main.c:499` | `HAL_UARTEx_DisableFifoMode(&huart7)` | **FIFO 关闭**，只有 1 字节硬件缓冲 |
| 接收方式 | IT 单字节，115200 → 每 86.8µs 一次 RXNE | 必须 86.8µs 内响应，否则 ORE |

TIM4 的 5ms 任务里要跑 `Attitude_Update + Odom_Update + Nav_Update + Chassis_Update`，其中 `Chassis_Update` 一次下发 4 帧 CAN。**只要这次 ISR 超过 86.8µs，UART7 就会溢出丢字节**（HAL 会进 `ErrorCallback` 重启接收，不会死锁，但那一帧 `Y` 就废了）。

**修法**：`stm32h7xx_hal_msp.c:451` 改 `(2,0)`（低 TIM4 一级）。若还想更稳，可打开 UART7 FIFO（`HAL_UARTEx_EnableFifoMode`）——但那属于用户自配区域，需你点头。

## 4. P1-4：`main.c` 初始化顺序导致 UART7 缓冲溢出

```c
148  Link_Init();            /* 发 K,1、启动状态机 */
...
154  Attitude_Calibrate(400);  /* 阻塞 400ms */
157  Time_Init();               /* 5ms 控制任务开始跑 */
160-164  5× SetEnable(Disable);
165  HAL_Delay(1000);           /* ★ 阻塞 1 秒 */
167-170  4× SetEnable(Enable);
174  Nav_ResetPose(45,45);
176  printf(...);
181  while (1) { Debug_Task(); Link_Poll(); }   /* 才开始轮询 */
```

从 `Link_Init()` 到第一次 `Link_Poll()` 约 **1.4 秒**。这期间：
- UART7 的字节由 `HAL_UART_RxCpltCallback` → `Link_FeedByte()` 收进环形缓冲 ✅ 不丢；
- 但环形缓冲只有 **128 字节**（`Link.c:6` `FR_RX_SZ 128`），且 `Link_FeedByte()` **没有满判断**（`Link.c:217~221`）——满了直接覆盖未读数据；
- F103 在前 1 秒 `link_lost=0`，会以 100Hz 发 `Y`（每帧约 20 字节）→ **1 秒就 2000 字节**，远超 128；
- 结果：这 1.4 秒内 `E,1` 与 `Y` 相互覆盖，成帧错乱。

**实际后果有限**（F103 会持续补发 `E,1`，成帧状态机也能靠 `<<` 重新同步），但这是设计缺陷。

**建议（任一）**：
1. 把 5 个 `SetEnable` / `HAL_Delay(1000)` / `Attitude_Calibrate` 全部挪到 `Link_Init()` **之前**；
2. 或把 `Link_Init()` 挪到最后（`Nav_ResetPose` 之后）；
3. 或给 `Link_FeedByte()` 加满判断（丢新字节而不是覆盖）。

推荐 **2**：`Link_Init()` 紧贴 `while(1)` 之前，语义最清楚。

## 6. P1-7：A* 堆容量偏小

`s_heap_push()` 的容量保护是 `MAP_CELLS * 2 = 4608`，但算法**允许同一格重复入堆**（没有 closed set，只靠 `ng < s_g[]` 过滤）：

- 格数 2304，每格最坏被改进 8 次 → 理论上限 18432 次 push；
- 实际通常在 2~3 次/格（≈7000），**超过 4608**；
- 一旦堆满，`s_heap_push()` 直接 `return` 丢弃节点 → 可能**找不到路径或路径次优**，且无任何提示。

**修法（二选一）**：
1. 堆数组放大到 `MAP_CELLS * 8`（+36KB RAM，H723 有 320KB，够）；
2. 加 `s_closed[MAP_CELLS]`，`s_heap_pop()` 后跳过已扩展节点（更省内存，还能提速）。

推荐 **2**。

> 其余 A* 逻辑核对正常：`s_g` 用 `uint16_t` 最大代价 32256 < 65535 不回绕；`s_par` 用 `int16_t` 存 0~2303 安全；回溯有 `max_cells` 保护；`s_q` 有 `tail < MAP_CELLS` 保护。
