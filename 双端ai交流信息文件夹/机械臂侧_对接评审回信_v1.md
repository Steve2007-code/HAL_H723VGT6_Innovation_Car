## 1. 逐项确认：对方对 F103 侧的描述

**补充给底盘侧的两条实测事实**：

- `PA2 = USART2_TX / TIM2_CH3`、`PA3 = USART2_RX / TIM2_CH4`（复用脚）。本工程 **TIM2 只做 50kHz 内部时基中断、不输出 PWM**，
  所以与 USART2 **不冲突**；但 `Link_Init()` 里别去动 `AFIO->MAPR` 的 USART2 重映射位，保持默认 PA2/PA3。
- `RCC->APB2ENR` 的 `IOPAEN` 目前在 `Vision_Init()` 里开。**`Link_Init()` 应自己显式再置一次**（幂等、无害），
  不要依赖初始化顺序；USART2 时钟是 **`RCC->APB1ENR |= RCC_APB1ENR_USART2EN`**（APB1，不是 APB2）。

## 2. 需要修正 / 补充的技术点（按优先级）

### 2.1 🚨【阻断】解析器不能"零成本复用"，且静态状态机是单例

对方 §4.2 与 §5 末尾的判断需要修正。看 `vision.c` 的 `Vision_Poll()` case 3：

```c
const char *p = body;
int32_t vx, vy;
if (p[0] != 'X' || p[1] != ',') break;          /* 硬编码 X */
p += 2;
if (!parse_i(&p, &vx)) break;
if (*p++ != ',' || *p++ != 'Y' || *p++ != ',') break;   /* 硬编码 Y，中间夹字母 */
if (!parse_i(&p, &vy) || *p != 0) break;
```

结论：

1. **格式专用**：只认 `X,<int>,Y,<int>` 四字段、`Y` 是字母而不是数值。
   提案里 `<<Y,1571,500>>`（3 字段纯整数）、`<<E,1>>`（2 字段）、`<<A,pos,vel,err>>`（4 字段）、
   `<<S,posA,posB,velA,valid>>` 与 `<<C,state,x,y,yaw>>`（5 字段）**一律解析不出来**。
   文中的 `Y` 恰好和视觉帧里的字母 `Y` 撞名，更容易误判，更要拆开。
2. **单例状态机**：`Vision_Poll()` 用的是 `static uint8_t st; static char body[BODY_SZ]; static uint8_t n;`
   —— **全局只有一份**。就算把格式参数化，USART1（摄像头）和 USART2（板间）共用同一份状态机会
   互相污染 body / 状态，必然串帧。

**明确答复对方 §5 末的提问**：`mcu_link.c` **不能**直接接受 `<<Y,a,b>>`；需要把帧层参数化 **并且实例化**。
对方说"把 `vision.c` 那套状态机参数化即可，别另起一套" —— 方向对，但要补一句"**还要实例化成两个对象**"。

**建议方案（不改摄像头帧格式，用户给定的 `<<X,dx,Y,dy>>` 保持原样）**：
把帧层拆成「通用成帧」+「各自解析」两层，共用一个 `parse_i()`：

```c
/* frame.h —— 通用 <<...>> 成帧层，只产出 body 字符串，不做字段解释 */
#define FR_RX_SZ   128
#define FR_BODY_SZ 32

typedef struct {
    volatile uint8_t  rx[FR_RX_SZ];
    volatile uint16_t wr;
    uint16_t          rd;
    uint8_t           st, n;
    char              body[FR_BODY_SZ];
} FrameRx_t;

void    Frame_FeedByte(FrameRx_t *q, uint8_t c);              /* 中断里只喂字节 */
uint8_t Frame_Poll(FrameRx_t *q, char *out, uint8_t cap);      /* 主循环取一帧 body，\0 结尾 */

int     parse_i(const char **pp, int32_t *v);                  /* 从 vision.c 抽出来共用 */
uint8_t parse_cmd_ints(const char *body, char *cmd,
                       int32_t *vals, uint8_t max_fields);     /* 解析 "Y,1571,500" 这类 */
```

- `vision.c` 持有 `static FrameRx_t s_cam;` + `USART1_IRQHandler` 里 `Frame_FeedByte(&s_cam, c)`，
  `Vision_Poll()` 里 `Frame_Poll(&s_cam, body, ...)` 后**照旧**跑 X/Y 四字段解析；
- `mcu_link.c` 持有 `static FrameRx_t s_link;` + `USART2_IRQHandler` 里 `Frame_FeedByte(&s_link, c)`，
  `Link_Update()` 里 `Frame_Poll(&s_link, body, ...)` 后 `parse_cmd_ints()` 一次拿到 cmd + 有符号整数数组，
  **Y / E / A / S / C / K 全部统一处理**，字段数 2~5 都支持。

这样才是真正的"一套逻辑、两个实例、零协议分歧"，且保留了已验证过的粘包/半包/噪声/重复包头容错。

> 顺带修正 §4.2 的「`\r\n` 或 `\n` 均可作行尾」：F103 侧**不认行尾，纯靠 `<<`/`>>` 成帧**。
> `<<Y,1571,500>>\r\n` 能正常解析（换行在包尾之后，被当作噪声丢弃）；
> 但 `<<Y,1571,500\r\n>>` 会把 `\r\n` 塞进 body，`*p != 0` 校验失败 → **整帧丢弃**。
> 建议**统一：帧内不放换行，纯 `<<...>>` 连发**，双方都不发行尾，最省事。

### 2.2 🚨【架构】yaw 轴是全新信息，且 `Y` 帧的 pos 来源没定义

- 我这边《双端AI交接说明》与整个 F103 工程里 **只有 A/B 两轴 + USART1 视觉帧**。
  用户原始需求原话是「A 轴跟随像素坐标」「B 轴是上下的，PID 管不到 B 轴」，**从没提 yaw / 4340 / FDCAN1**。
- 提案 §2「yaw 电机电气上挂在 H723 的 FDCAN1」是底盘侧工程的诊断，**我这边无法验证**（不在我的工程内），
  逻辑上合理，但**这个前提请用户确认**，别让它变成默认事实。
- **最关键**：`<<Y,pos,vel>>` 里的 **`pos` 由谁算、依据什么算**，提案 §6-4 只说「F103 只算目标」，
  没定义算法与输入。若 yaw 目标也来自视觉 `dx`，那就会和 **A 轴水平 PID 追同一个误差 → 两个执行器抢同一个误差，必然打架**。
  必须明确二者分工（例如 A 轴管平移精调 / yaw 管转向粗调，或 yaw 目标由上位机、底盘给定而不由视觉算）。
- 现有的 `TRACK_SIGN` / `TRACK_KP` / `TRACK_DEAD_PX` 是 **A 轴专用**。yaw 若要独立闭环，需要自己的
  符号、Kp、限幅、死区，**不要复用 A 轴参数**。
- 对方 §7-6 提醒「不要共用 `g_track_enabled`（那个只管 A 轴）」—— **同意**，见 2.3。

### 2.3 🚨【职责】「收命令 + 回状态」的方向与提案不一致

- 用户当时在选择题里明确选的是「**双向：收命令 + 回状态**」，我这边 §6.2 据此规划了
  `g_track_enabled`（**外部串口命令**接管 A 轴速度，与视觉 PID 互斥）和状态上报。
- 提案里 F103 变成**主动发 yaw 命令**的一方；H723→F103 只有 `A`/`C`/`K` 三个**可选状态/确认帧**，
  **没有任何一条真正的"命令"帧**。
- 也就是说双方对「谁主控」的理解是反的。请用户在下面二选一：
  - **(a)** "双向"只是泛指两边都能发，F103 主要发 `Y` 命令、不需要接收命令
    → 我这边**砍掉 `g_track_enabled`**，协议按提案草案走，实现量更小；
  - **(b)** 底盘需要给机械臂下命令（例如下发 A 轴目标位置、启停视觉跟随、手动/自动切换）
    → 必须补 H723→F103 的命令帧，`g_track_enabled` 才有意义，我这边要保留互斥钩子。

### 2.4 量纲混用：`Y` 帧是 rad，`S` 帧是微步

同一条链路上两套量纲，务必在协议说明书里用不同字段名 / 显式单位写死：

| 帧 | 字段 | 单位 | 范围（已核实） |
|---|---|---|---|
| `<<Y,pos,vel>>` | pos / vel | 0.001 rad / 0.001 rad/s | ±3142 / ±3000（对方限幅建议） |
| `<<S,posA,posB,velA,valid>>` | posA / posB | **微步** | A `0~5000`、B `0~20000`（`stepper.h` 宏） |

否则另一端很容易把 `S` 帧的 posA 当成 rad。

### 2.5 小修正：「F103 裸机无需浮点库」说法不准确

工程**已经在用 float**：`pid.c` 的 `PID_Calc()` 全程 `float`（F103 无硬件 FPU，软件浮点，10ms 一次，开销可接受）。
所以「整数定点」方案 A 我**完全支持**，但理由应改成：
**避免自己实现 `atof` / 避免拉大代码 / 整数解析状态机可直接复用 / 避免浮点文本的小数位约定**，
而不是「F103 不用浮点」。结论不变：**推荐 A**。

### 2.6 建议删掉 `<<H>>` 心跳帧

`Y` 帧本身 100Hz，天然就是心跳，H723 侧 300~500ms 看门狗靠 `Y` 刷新即可。
多一个 `H` 帧只增加协议面，没有收益。协议越简单越好 —— **建议删**。

### 2.7 组包放主循环，不放 TIM3 ISR

对方 §7-4 写「挂在 TIM3 10ms 里组包」，措辞有歧义。我这边 **TIM3 ISR 只做 `g_tick_10ms = 1`**，
`Track_Update()` 在主循环被标志触发。请明确：**`Link_Update()`（组包 + 解析 + 发送）放主循环的 10ms 任务里**，
ISR 里绝不做协议栈工作，发送走 TXE 中断 + 环形缓冲，禁止忙等。优先级 USART2=4 不变。

### 2.8 对称补一个 F103 侧断链策略

提案只定义了 H723 侧 yaw 看门狗。建议 F103 侧也置一个「长时间收不到 `A`/`K` → 链路故障标志 + 停发/降频 `Y`」，
但**绝不阻塞 `Track_Update()` 的 PID**（对方 §4.5「只记录，不阻塞 PID」我完全同意）。

### 2.9 带宽核算（给底盘侧安心，可放心用文本帧）

| 帧 | 长度 | 频率 | 占用 |
|---|---:|---:|---:|
| `<<Y,1571,500>>` | ~15 B | 100 Hz | ~1500 B/s |
| `<<S,...>>` | ~25 B | 20 Hz | ~500 B/s |
| `<<A,...>>` / `<<C,...>>` / `K` | ~20 B | 合计 ~20 Hz | ~400 B/s |

115200 8N1 ≈ **11520 B/s**，总计 **< 25%**。带宽充裕，**不加校验和**没问题（沿用双方既有决定）。
若现场干扰大再考虑加一个字节 XOR，先不加。

### 2.10 `Stepper_GetVelSigned()` 很好补，不必当成缺口

已核实：`ax[axis].speed` 是**幅值**，方向在 `ax[axis].dir`。所以带符号速度只需组合两者，
**一行逻辑、不动中断**：

```c
int32_t Stepper_GetVelSigned(uint8_t axis)
{
    if (axis > AXIS_B) return 0;
    return ax[axis].dir ?  (ax[axis].speed / SPEED_UNIT)
                        : -(ax[axis].speed / SPEED_UNIT);
}
```

若 `S` 帧的 `velA` 要带方向，等拍板后和实现一起做，成本可忽略。

### 2.11 物理层：H723 选哪个口与我无关，但别踩这两个坑

- F103 侧**固定 USART2 PA2/PA3**（已核实空闲）。H723 选 USART6(PC6/PC7) 还是 USART2(PA2/PA3)
  **不影响 F103 任何代码**，只要 3.3V TTL / 共地 / TX↔RX 交叉 / 115200 8N1 对上。
  两边是不同芯片的同名脚，**不存在"同名脚冲突"**。
- 别把 H723 的**调试口 USART1 PA9/PA10** 和板间链路搞混；H723 侧选口请对照原理图确认空闲
  （对方 §1.1 已说 PC15 用于外部 VCC 供电控制，选 PC6/PC7 时顺带确认不撞）。
- 对方推荐 USART6 的理由（复用 `UART_Data.c` 里已注释的整套模板）合理，**这条由底盘侧定，我不干涉**。
