## 0. 三分钟速览（先读这一节）

### 0.1 系统由三块组成

```
┌──────────────┐   USB摄像头    ┌───────────┐   UART 115200   ┌──────────────┐
│  PC (Python) │ ─────────────► │ 视觉计算   │ ──────────────► │ F103 机械臂   │
│  YOLO 识别   │                │ <<X,dx,Y,dy>> │  USART1      │ 直角坐标机器人 │
└──────────────┘                └───────────┘                 └──────┬───────┘
                                                                      │ USART2 ↔ UART7

                                                                      │ <<A>>/<<K>> ↑
                                                               ┌──────▼───────┐
                                                               │ H723 底盘     │
                                                               │ 麦轮+A*导航   │

                                                               │ 达妙 4310P ×4 │
                                                               └──────────────┘
```

### 0.2 一句话讲清分工

- **PC 视觉**：只负责「目标在哪」，输出像素偏差。
- **F103（机械臂）**：只负责「对准目标」。A 轴步进追 **dy**，yaw 轴追 **dx**，两轴解耦。
- **H723（底盘）**：只管「走到哪」。地图导航 + 麦轮运动学 + **代 F103 发 yaw 的 CAN 指令**（F103 自己没有 FDCAN 接 4340）。

### 0.3 最容易踩的三个坑（详见 §10）

1. **视觉端 dx/dy 的符号被改过了**，和 F103 里的 `TRACK_SIGN` / `YAW_SIGN` 现在**冲突**，不处理就会两轴全反。
2. **yaw 实际限速是 3000 mrad/s 不是 6000**（`link_config.h` 里把 `YAW_VEL_MRADPS=6000` 又钳回 `LINK_VEL_MAX_MRADPS=3000`）。
3. **F103 的 `STEPPER_STEPS_PER_REV=1600`（1/8 细分）与实际拨码 32 细分不符**，注释和代码互相矛盾。

## 1. 硬件与引脚总表

### 1.1 STM32F103C8T6（机械臂）

| 功能 | 外设 | 引脚 | 配置 | 备注 |
|---|---|---|---|---|
| 顶视相机 | USART1 | **PA9 = TX / PA10 = RX** | 115200 8N1，`BRR = SystemCoreClock/baud = 625` | 只收不发，`CR1 = UE\|RE\|RXNEIE` |
| 板间链路 | USART2 | **PA2 = TX / PA3 = RX** | 115200 8N1，`BRR = (SystemCoreClock/2)/baud = 312` | **必须按 36MHz 算**，照抄 USART1 的 72MHz 会错一倍 |
| A 轴步进（水平伸缩） | TIM2 软脉冲 | **STEP=PA7 / DIR=PA6 / EN=PA5** | 推挽 2MHz | 32 细分，行程 0~6500 步 |
| B 轴步进（上下） | TIM2 软脉冲 | **STEP=PB0 / DIR=PB1 / EN=PB10** | 推挽 2MHz | 只使能不参与 PID，行程 0~20000 步 |
| 状态灯 | GPIO | **PC13** | 推挽 2MHz，**低电平亮** | 识别到目标常亮 |

**时钟**：72 MHz（`SystemCoreClock`），CMSIS 裸机，无 HAL、无 CubeMX、无 FreeRTOS。

**中断优先级**（数值越小越高）：

```
TIM2 (50kHz 脉冲) = 1  >  TIM3 (10ms 节拍) = 2  >  USART1 (相机) = 3  >  USART2 (板间) = 4
```

> 设计意图：脉冲绝不能丢，所以 TIM2 最高；相机比板间优先（视觉是主输入）。

### 1.2 STM32H723VGT6（底盘）

| 功能 | 外设 | 引脚 | 配置 |
|---|---|---|---|
| 板间链路 | **UART7** | **PE7 = RX / PE8 = TX**（AF7） | 115200 8N1，`ClockPrescaler=DIV1`，**FIFO 关闭** |
| 调试串口 | USART1 | PA9 / PA10 | 115200，命令行 + CSV 遥测 |
| 底盘电机 ×4 | FDCAN1 | — | 1 Mbps，指令 `0x200+ID`，回传 `0x11~0x14` |
| IMU | FDCAN3 | — | DM-IMU-L1，CANID 0x06，回传 0x16 |
| yaw 轴 4340P | FDCAN1 | — | CANID 0x05，指令 **0x105**，回传 0x15 |
| WS2812 灯 | SPI6 + BDMA | — | 缓冲区必须在 D3 SRAM4 |
| 时基 | TIM4 | — | 1 ms 中断，控制链 200 Hz |

> ⚠ **UART7 是用户自己配的，两个 AI 都没碰过 `MX_UART7_Init()`**。改之前先看 `Core/Src/main.c:468`。

### 1.3 板间接线（最容易接错）

```
F103 PA2 (TX) ────► H723 PE7 (RX)
H723 PE8 (TX) ────► F103 PA3 (RX)
F103 GND      ────  H723 GND      ← 必须共地，否则必现乱码
```

**3.3V TTL 直连，TX/RX 交叉**。两个 MCU 都是 3.3V，不需要电平转换。

### 1.4 达妙电机对应关系（H723）

| CANID | 位置 | 轮型 | 数据块 |
|---|---|---|---|
| 0x01 | 左前 | A（左旋） | `DM_Motor_4310P_Next_StructData` |
| 0x02 | 右前 | B（右旋） | `DM_Motor_4310P_StructData` |
| 0x03 | 左后 | B（右旋） | `DM_Motor_4310_StructData` |
| 0x04 | 右后 | A（左旋） | `DM_Motor_4310_Next_StructData` |
| **0x05** | **yaw 轴 4340P** | — | **`DM_Motor_4340P_Yaw_StructData`** |

方向系数默认 `{+1, -1, +1, -1}`（实车标定值）。

路径：`CMSIS _F103C8T6_Cartesian_Robot/`

| 文件 | 职责 | 谁在调 |

| `track.c/.h` | **A 轴闭环**：取视觉帧 → 低通 → PID → `Stepper_SetVel()`。同时提供全局时基 `g_ms` | `main.c` |
| `track_config.h` | **A 轴全部可调参数**（标定只改这里） | — |
| `vision.c/.h` | USART1 收 `<<X,dx,Y,dy>>`，成帧 + 解析 | `track.c` |
| `yaw_track.c/.h` | **yaw 闭环**：dx → 增量式 PD → yaw 目标角 | `main.c` |
| `link_config.h` | **板间链路 + yaw 全部参数** | — |
| `mcu_link.c/.h` | USART2 板间链路：收 A/K、发 Y/E、握手、看门狗 | `main.c` |
| `frame.c/.h` | 通用 `<<...>>` 成帧状态机（**每路数据流一个实例**，绝不能共用） | `vision.c` / `mcu_link.c` |
| `pid.c/.h` | 浮点 PID（A 轴用） | `track.c` |

### 2.1 主循环时序（`main.c`）

```c
while (1) {
    if (g_tick_10ms) {          // TIM3 每 10ms 置位
        g_tick_10ms = 0;
        Link_PollRx();          // 1) 先收 A/K，刷新链路状态 + 4340 实际角度
        Track_Update();         // 2) A 轴：视觉 PID → Stepper_SetVel
        YawTrack_Update(Track_GetDx(), Track_GetDy(), Track_GetValid());  // 3) yaw 增量 PD
        Link_TxTick();          // 4) 补发 E,1 + 组 Y 帧投递 TX 缓冲
    }
    led_on/off;                 // 识别到目标常亮
}
```

**顺序不能换**：`Link_PollRx()` 必须最先（yaw 的超前量限幅要用最新的 4340 实际角度 `Link_GetYawPos()`）。

**全程非阻塞**：ISR 只收/发字节，组包和协议在主循环，没有任何 `while` 忙等。

### 2.2 stepper 的 4 种模式

```c
MODE_IDLE  = 0   // 停
MODE_JOG   = 1   // 连续跑，直到 Stop
MODE_POS   = 2   // 走到目标位置自停（MoveTo / MoveSteps）
MODE_TRACK = 3   // 连续速度跟随（视觉 PID 专用，Stepper_SetVel）
```

`MODE_TRACK` 的关键特性：**可以每 10ms 反复调用 `Stepper_SetVel()`，内部只改目标速度、不重启加减速斜坡**，所以连续跟随不会抖、不丢步。这是 A 轴能平滑跟的关键。

脉冲生成：TIM2 50 kHz 中断（20 µs 一拍），每拍把速度累加到 `acc`，超过阈值就翻转 STEP 引脚。速度单位 pps，内部用 `SPEED_UNIT=10` 定点放大。

## 3. A 轴闭环：视觉 y 误差 → 步进

### 3.1 数据流

```
<<X,dx,Y,dy>> ──USART1 ISR──► frame.c 成帧 ──► Vision_Poll() 解析
    ──► Track_Update() 取最新帧（把缓冲里所有帧读完，只留最后一帧）
    ──► 一阶低通 (TRACK_LPF_ALPHA=0.5)
    ──► PID_Calc()（只有 P，KI=KD=0）
    ──► 小误差保底速度 TRACK_MIN_PPS
    ──► Stepper_SetVel(AXIS_A, TRACK_SIGN * v)
```

### 3.2 参数（`track_config.h`，标定只改这一个文件）

| 宏 | 当前值 | 含义 / 调法 |
|---|---|---|
| `TRACK_UART_BAUD` | 115200 | 相机串口波特率 |
| `TRACK_TIMEOUT_MS` | 250 | 超过这么久没新帧判丢目标（30fps 下约 7.5 帧） |
| `TRACK_PERIOD_MS` | 10 | PID 周期 |
| `TRACK_SIGN` | **+1** | **方向符号**。跑反了就改 -1 |
| `TRACK_KP` | 72.0 | 单位 pps/px。36→72 提过一倍响应 |
| `TRACK_KI` / `TRACK_KD` | 0 | 故意为 0，纯 P |
| `TRACK_DEAD_PX` | 5 | 死区，抑制像素抖动 |
| `TRACK_OUT_MAX_PPS` | 12000 | 输出限幅，与 `MAX_PPS` 同步 |
| `TRACK_MIN_PPS` | 600 | 小误差保底速度（300→600 提过） |
| `TRACK_INTEG_MAX` | 200.0 | 积分抗饱和（KI=0 时实际不起作用） |
| `TRACK_ACC_PPS_PER_MS` | 24 | 速度斜坡，到 12000pps 约 500 ms。**丢步就降回 16** |
| `TRACK_LPF_ALPHA` | 0.5 | dy 低通，1.0 = 不滤波 |
| `LOST_SENTINEL` | 9999 | 视觉端表示「没识别到」的哨兵值 |

### 3.3 为什么 A 轴用纯 P 就够（重要设计理由）

A 轴是**速度伺服**（直接给 pps），没有「目标位置」这个中间量，也没有积分器。
`v = KP × dy` 本身就是「误差越小速度越慢」的比例控制，**天然具备软着陆**，所以不需要 yaw 那套超前量限幅。

它如果出现过冲，来源是**减速斜坡太陡**（`TRACK_ACC_PPS_PER_MS` 太大或太小），而不是积分饱和。

**小误差的问题是另一个**：纯 P 在误差接近 0 时输出也接近 0，表现为「蹭着走、特别慢」。所以加了 `TRACK_MIN_PPS=600` 保底，死区外强制至少 600 pps，由斜坡平滑加速不会突变。

### 3.4 丢目标时的行为

```c
if (!s_valid || Vision_AgeMs() > TRACK_TIMEOUT_MS) {
    PID_Reset(&s_pid);
    g_track_valid = 0;
    Stepper_SetVel(TRACK_AXIS, 0);   // 按斜坡平滑减速停住，不硬停
    return;
}
```

**不会急停**，走速度斜坡归零。yaw 那边则保持目标角不动（见 §4.4）。

## 4. yaw 闭环：视觉 x 误差 → 4340P（经 H723 代发）

### 4.1 为什么 F103 不能直接控 4340

F103C8T6 没有 FDCAN（只有 bxCAN，且工程里没接）。所以：

```
F103 算出 yaw 目标角 ──<<Y,pos,vel>>──► H723 ──CAN 0x105──► 4340P
                                            ◄──CAN 0x15──
                ◄──<<A,pos,vel,err>>──
```

**F103 只给目标角，位置环在 4340 内部**。F103 不做位置闭环，只做「目标角怎么走」的规划。

### 4.2 控制律（增量式 PD）

```c
phi = dx;                          // 只追 x 像素误差，dy 完全不参与
if (在死区内) {清零低通状态; return;}
s_phi_f += ((phi - s_phi_f) * YAW_LPF_Q12) >> 12;    // 一阶低通 0.5
dphi = s_phi_f - s_phi_prev;                          // 微分
dphi 限幅 ±800                                        // 防像素噪声放大
d = (s_phi_f*YAW_KP_Q12 + dphi*YAW_KD_Q12) >> 12;     // Q12 定点
if (d==0 && s_phi_f!=0) d = ±4;                       // Q12 截断补偿
d 限幅 ±YAW_RATE_MAX_MRAD
if (YAW_SIGN<0) d = -d;
s_target_mrad += d;                                   // 增量累加
```

### 4.3 两个关键保护（这是 yaw 不超调的核心）

**① 超前量限幅（防积分饱和）**

```c
lead = s_target_mrad - Link_GetYawPos();    // 目标角领先实际角多少
if (lead >  cap) s_target_mrad = Link_GetYawPos() + cap;
if (lead < -cap) s_target_mrad = Link_GetYawPos() - cap;
```

物理事实：**超调量 ≈ 转速 × 延迟**（5 rad/s × 100 ms ≈ 500 mrad = 28.6°），**与 KP/KD 无关**。
只要目标角不允许领先实际位置太多，积分饱和就被物理杜绝，于是 **KP 可以放心调大来提速**。

**② 软着陆**

```c
cap = YAW_LEAD_MAX;                        // 大误差：全速
if (ae < YAW_SLOW_PX) cap = YAW_LEAD_MAX * ae / YAW_SLOW_PX;   // 小误差：线性收紧
if (cap < 20) cap = 20;                    // 保底 20 mrad，保证最后能贴上
```

**③ 视觉帧门控（必须保留）**

```c
if (g_last_frame_ms == s_seen_ms) return;   // 同一帧不重复累加
s_seen_ms = g_last_frame_ms;
```

`YawTrack_Update()` 以 100 Hz 被调用，但相机只有 30 fps。**同一帧被重复累加 2~3 次会让目标冲过头→反向修正→来回震荡**。这是实车踩过的坑。

**④ 死区内必须清零低通状态**

```c
if (phi > -YAW_ANGLE_DEAD && phi < YAW_ANGLE_DEAD) {
    s_phi_f = 0;  s_phi_prev = 0;  return;   // 不是把 phi 置 0 就走低通
}
```

只把 phi 置 0 再走低通的话，`s_phi_f` 的残留会让目标继续动 → 过冲 → 原点附近来回摆。

### 4.4 参数（`link_config.h`）

| 宏 | 代码实际值 | 含义 |
|---|---|---|
| `YAW_SIGN` | +1 | 方向符号 |
| `YAW_KP_Q12` | 2800 | 比例项 ≈ 2800/4096 ≈ 68% |
| `YAW_KD_Q12` | 5000 | 微分阻尼 |
| `YAW_ANGLE_DEAD` | 5 px | 像素死区 |
| `YAW_RATE_MAX_MRAD` | 200 | 每帧最大角度增量（30fps × 200 = 6000 mrad/s） |
| `YAW_LPF_Q12` | 2048 | 一阶低通 0.5 |
| `YAW_VEL_MRADPS` | 6000 | **想**发给 4340 的限速 |
| `YAW_LEAD_MAX` | **1000** | 领头量上限 mrad |
| `YAW_SLOW_PX` | **100** | 软着陆起点像素 |

### 4.5 上电默认目标角 = 0 的后果

`LINK_YAW_DEFAULT_MRAD = 0` 意味着**一上电 4340 就往 0 位（0°）走**。
联调时要注意**机械限位与线缆缠绕**——这是底盘侧专门提过的坑点。

## 5. 板间通信协议（F103 USART2 ↔ H723 UART7）

### 5.1 帧集

| 方向 | 帧格式 | 频率 | 含义 |
|---|---|---|---|
| F103 → H723 | `<<Y,pos_mrad,vel_mradps>>` | **100 Hz**（每 10 ms） | yaw 目标角 + 限速，单位 0.001 rad / 0.001 rad/s |
| F103 → H723 | `<<E,1>>` | 上电立即 + 每 100 ms 补发直到收到 `K,2` | 请求使能 4340（**幂等**） |
| H723 → F103 | `<<A,pos,vel,err>>` | **20 Hz**（50 ms） | 4340 实际角度 / 速度 / 错误字节 |
| H723 → F103 | `<<K,code>>` | **事件触发，各只发一次** | 1 上电就绪 / 2 已使能 / 3 非法帧 / 4 限幅 / 5 断链 |

**成帧**：`<<` 起、`>>` 止、纯 ASCII、帧内无换行、**无校验和**。
**解析**：白名单 `Y E A S C K`（大小写敏感，小写一律判非法）。`S`/`C` 本期未实现。

### 5.2 握手状态机（含「等待」的全部细节）

```
时间线（正常上电）：
F103 上电 ──► 立即发 E,1 ──► 每 100ms 补发 E,1（同时 100Hz Y 照发）
H723 上电 ──► 发 K,1（就绪，不参与链路活性判定）
           ──► 收到 E,1 ──► DM_CAN_Motor_SetEnable(4340, 使能) ──► 回 K,2
F103 收到 K,2 ──► 置 s_yaw_ack=1 ──► 停止补发 E,1
H723 开始收到 Y ──► 转发 0x105 ──► yaw 动
```

**关键设计：F103 发完 `E,1` 不等待、不阻塞**，不引入 ACK 状态机。
`K,2` 只是「后台低频补发」的停止信号。100 Hz 的 `Y` 全程照发。

### 5.3 为什么 `E,1` 要一直补发到收到 `K,2`（重要历史）

最初写的是「上电前 1 秒每 100 ms 补发」，条件 `elapsed < 1000 || link_lost`。
底盘侧复核时发现**竞态**：

> H723 的 `A` 帧是**无条件 20 Hz**（不看是否使能、不看断链）。
> H723 晚起时，它的第一帧 `A` 会在 **≤50 ms** 内到达 F103，把 `link_lost` 清掉。
> 而 `E,1` 补发周期是 100 ms、窗口只剩 ≤50 ms → **约一半概率 H723 一帧 `E,1` 都收不到** → 永远失能 → yaw 不动，且双方都无异常提示。

反直觉点：**恰恰是「A 帧无条件 20Hz」把唤醒提前，让「只在 link_lost 期间补发」失效。**

所以改成：只要没收到 `K,2` 就一直每 100 ms 补发，与任何上电时序无关。

### 5.4 自愈链

| 场景 | 行为 |
|---|---|
| 两板同时上电 | H723 收 `E,1` → 回 `K,2` → 停止补发 |
| **H723 晚起 >1s** | F103 一直没收到 `K,2` → 持续补发 → H723 一起来必收到 → 使能 → 回 `K,2` → 停止 |
| **H723 中途重启** | 发 `K,1` → F103 收到后**清 `s_yaw_ack`** → 重新补发 `E,1` → yaw 自动复活 |
| F103 先起、H723 后起 | 同上 |

### 5.5 看门狗（两侧各一把）

| 侧 | 条件 | 动作 |
|---|---|---|
| **H723** | 400 ms 没收到 `Y` | 置 `s_link_lost`、**停发 0x105**、**保持当前位置**、回一次 `K,5` |
| **F103** | 1 s 没收到任何 `A`/`K` | 置 `link_lost`、**停发 `Y`**（PID 不受影响，A 轴继续跟视觉） |

**单向断链的特殊处理**（F103→H723 断、H723→F103 通）：
F103 仍能收到 `A` → `link_lost` **不会置位** → F103 继续发 `Y`。
**这是预期行为、且是自愈所需**：链路修好后 H723 收到 `Y` 立即恢复；若此时停发 `Y` 反而死锁。
安全由 H723 的 400 ms 看门狗兜底。**不要"修"这个。**

### 5.6 限幅（两侧必须逐字一致）

| 量 | F103 (`link_config.h`) | H723 (`Link.h`) | 实际生效值 |
|---|---|---|---|
| `Y.pos` | 0 ~ 3142 mrad | 0 ~ 3142 | **0 ~ 180°**，不允许负值 |
| `Y.vel` | ±`LINK_VEL_MAX_MRADPS` = **3000** | ±`LINK_VEL_LIM` = 6000 | **±3000（F103 先钳了）** |

> ⚠ **这是当前的一个不一致**：`yaw_track.c` 里 `Link_SetYawTarget(target, YAW_VEL_MRADPS=6000)`，但 `Link_TxTick()` 又按 `LINK_VEL_MAX_MRADPS=3000` 钳位，所以**发出去的 vel 永远是 3000**。
> 效果：yaw 实际最高 3 rad/s，不是 README 说的 6 rad/s。
> 想真上 6 rad/s，把 `link_config.h` 的 `LINK_VEL_MAX_MRADPS` 改成 6000 即可（H723 侧已放开到 6000）。

### 5.7 带宽

文本帧，最长的 `A` 帧约 20 字节 × 20 Hz = 400 B/s，加 `Y` 帧 100 Hz × 约 16 B = 1600 B/s，**总占用 < 25%**（115200 下约 11.5 KB/s）。

### 6.2 `Link_Poll()` 五步

```c
1) while (s_frame_poll()) { 解析并分发 }
     cmd=='Y' && nf==2  ──► 限幅 → 存 s_yaw_pos/s_yaw_vel → 刷 400ms 看门狗
                            → 清 s_link_lost → 未使能则**只刷看门狗不转发**
                            → 已使能则 s_can_pending=1（覆盖语义，粘包取最新）
                            → 触发限幅则回 K,4（500ms 冷却）
     cmd=='E' && nf==1  ──► v==1: 未使能才 Enable 并回 K,2（幂等，重复补发无害）
                            v==0: Disable 并清 s_can_pending
                            其它: 回 K,3
     其它（A/S/C/K 上行）──► 属异常（自环/接错线），回 K,3（500ms 冷却）

2) 看门狗：!lost && (now - s_last_y_ms >= 400) ──► 置 lost、清 pending、回一次 K,5

3) CAN 代发：pending && !lost && enabled && (now - s_last_can_ms >= 10)
              ──► DM_CAN_Motor_Position_Speed(&DM_Motor_4340P_Yaw_StructData,
                                              s_yaw_vel, s_yaw_pos)
              ──► 即 CAN 帧 0x105，8 字节小端 float

4) A 帧 20Hz：无条件上报（不看使能、不看断链）
     v[0] = POS*1000  (mrad)
     v[1] = VEL*1000  (mrad/s)
     v[2] = UpData[0] (原始错误字节，F103 只存不解释)

5) s_tx_pump()：TX 环形缓冲 256B → 每次最多 64B 走 HAL_UART_Transmit_IT
               gState 不是 READY 直接返回，失败即丢，不重试不忙等
```

### 6.4 关键点：`0x105` 的节流与覆盖

- F103 发 100 Hz `Y`，H723 最快 100 Hz（10ms 节流）转发，频率匹配。

- **使能前收到 `Y` 只刷看门狗、不排队**，避免使能瞬间冲出一堆过期目标。

### 8.1 H723 世界系

| 项 | 约定 |
|---|---|

### 8.2 相机像素系（关键，容易搞错）

**历史坑**：早期用极角 `phi = atan2(dx, -dy)`，但本机相机是 **y 向上为正、x 向右为负**（与标准图像坐标双轴翻转）。目标在画面上方时 `-dy` 为负，`phi` 落在 ±180° 附近并在 ±π 处跳变 → **剧烈抖动**。

**所以改成：yaw 只追 `dx`，A 轴只追 `dy`，两轴彻底解耦。**

> `main.c` 和 `yaw_track.h` 里还留着「追极角 atan2(dx,-dy)」的**过时注释**，实际实现是追 `dx`。别被注释骗。

## 10. 当前已知问题与限制（**接手必读**）

### 10.1 🔴 视觉符号与 F103 方向参数冲突（最高优先级）

**事实**：
- 视觉端现在是 `dx = 中心 − 标定点`，**dx>0 表示目标在左侧**。
- F103 `track_config.h` 注释写的是「dx > 0 表示目标在画面右侧」（原始约定）。
- `yaw_track.c` 直接 `phi = dx;` 且 `YAW_SIGN = +1`。
- `track.c` 里 `Stepper_SetVel(AXIS, TRACK_SIGN * v)`，`TRACK_SIGN = +1`。

**后果**：两轴都会**朝反方向跑**，越跑越远，然后丢目标停住。

**两种修法（选一个，别两边都改）**：

| 方案 | 操作 |
|---|---|
| A（改 F103） | `track_config.h` 的 `TRACK_SIGN` 改 **-1**；`link_config.h` 的 `YAW_SIGN` 改 **-1**。改完必须实车验证 |
| B（改视觉） | 把 `live_detect.py` 的两行符号改回 `ax - cx0` / `ay - cy0` |

**推荐 B**：视觉端本来就是按 F103 的约定写的，把它改回去只需要动 2 行，不用重编译 F103、不用重新标定方向。

### 10.2 🟡 yaw 实际限速只有 3000 mrad/s

见 §5.6。`link_config.h` 的 `LINK_VEL_MAX_MRADPS=3000` 把 `YAW_VEL_MRADPS=6000` 钳掉了。
要真上 6 rad/s：改 `LINK_VEL_MAX_MRADPS` 为 6000。

### 10.3 🟢 `STEPPER_STEPS_PER_REV` 与实际细分不符（**只是死宏，不影响功能**）

`stepper.h:17` 写 `#define STEPPER_STEPS_PER_REV 1600`（注释说 1/8 细分），
但 `stepper.c` 注释和 README 都说 32 细分（200×32 = 6400）。

**2026-11-20 已核实：这个宏在 `stepper.c`/`track.c`/`main.c` 中一次都没被引用**，是纯注释性质的死宏。
真正决定行程的是 `AXIS_A_POS_MAX = 6500`（微步数，由拨码细决定物理长度）。

**影响**：无功能影响。但**换算物理距离时别用这个宏**——按实测拨码算：
若真是 32 细分，6500 微步 ≈ 1.02 圈丝杆；若 1/8 细分则 ≈ 4.06 圈。两者差 4 倍，量行程前先数拨码。

### 10.4 🟡 视觉端 `--target-up 100` 改变了 dy 的零点

现在 dy 的基准是「画面中心上移 100px 的红叉」，不再是画面中心。
**只有当机械臂/爪子相对相机的位置正好对应这 100px 时才对**。如果 F103 那边按「画面中心即对准」来理解，就会有 100px 的固定偏差。

### 10.5 🟡 H723 无绝对定位

位置全靠四轮轮速里程计，**麦轮横移打滑会累积误差**。
计划加二维码 / AprilTag / 顶视相机纠偏，目前未做。

### 10.6 🟡 H723 无电机掉线看门狗

丢帧时 `VEL` 保持旧值。需要在 `Motor_UpdateData` 加时间戳判断。

### 10.7 ✅ IMU 欧拉字段**已实测**：`euler[1]` 就是 yaw（2026-11-20 确认）

实测数据（同一次转动前后各读一次 `i`）：

| | `euler[0]` | **`euler[1]`** | `euler[2]` | `# yaw`（陀螺积分） |
|---|---|---|---|---|
| 转动前 | −1.28° | **9.69°** | 2.14° | 10.549° |
| 转动后 | 4.48° | **−61.34°** | −2.44° | −61.647° |

`euler[1]` 与陀螺积分 yaw 完全同步（差 0.3~0.9°，两帧时间差）。

**顺序确认：`euler[0]`=pitch、`euler[1]`=yaw、`euler[2]`=roll。**

⚠️ **`Attitude.h` 里 `ATT_EULER_FIELD 2` 是错的**，应为 **1**。
当前 `ATT_USE_EULER = 0`（欧拉慢速修正关闭）所以不生效；**一旦有人把它打开，yaw 会被往 roll(≈0) 上拉，越修越歪**。

### 10.7b 🟡 IMU 上电后约 300 ms 才响应轮询

实测上电后 `tx_err` 累计到 **31**（10ms 一次 ≈ 310ms）就不再增长。
而 `Attitude_Calibrate(400)` 在上电后立刻开始 → **前 300ms 采样全部失败**，bias 只用了最后约 100ms 的数据。

后果：`gz_bias` 精度不够（实测两次分别 0.00184 和 −0.00117 rad/s，折算 0.1°/s，60 秒漂 6°）。

**建议**：`main.c:153` 的标定前面加 `HAL_Delay(350)`，或把标定时长加到 800ms。
在线零偏学习（`NAV_IDLE` 且 `|gz−bias|<0.03` 时以 0.005 增益缓慢修正）能部分补偿，但初值差会先漂一段。

### 10.7c 🔧 IMU 链路排障方法（已内置计数器，2026-11-20 加的）

排查「yaw 不随转动变化」时，先敲 `i`，看新增的三行：

```
# att_upd=7752  imu rx total=7801  gyro=3877  tx_err=31
# last gyro frame: 02 00 02 80 F4 7F 17 80
# fdcan3 PSR=0x00000708 ECR=0x00000000
```

| 现象 | 结论 |
|---|---|
| `att_upd` 不涨 | TIM4 的 5ms 控制块没跑 |
| `rx total` 不涨 | 一帧 IMU 都收不到 |
| `gyro` 不涨但 `total` 涨 | 收到帧但类型字节不对（协议/固件问题） |
| `tx_err` 持续上涨 | 请求帧发不出去 → 查 PSR/ECR |
| `last gyro frame` 后 6 字节转动时不变 | 数据冻结 |
| `PSR & 0x80` | Bus-Off；`PSR & 0x07 == 3` = ACK 错误（IMU 没接/没电） |
| `(ECR>>8)&0x7F` | TEC，>128 Warning，>255 Bus-Off |

计数器定义在 `DM_IMU_L1_V1.0.c`（`g_imu_rx_total` / `g_imu_rx_gyro` / `g_imu_tx_err` / `g_imu_last_g`），
打印在 `Attitude.c:Attitude_PrintDiag()`。**排查完可以删，也可以留着（只占 300 字节）。**

> 另外：`i` 打印的 `acc x/y/z` **永远是 0.000，这是正常的**——`Attitude_Update()` 只请求 Euler 和 Gyro，
> 从来没调过 `Red_DM_IMU_accData()`，所以 `acc_f_raw[]` 一直是初值 0。不是 IMU 坏了。

### 10.7d ✅ 已加的两个 yaw 保护（2026-11-20）

**① 坏帧钳位（`Attitude.c`）**

实测发生过一次：车**完全没动**，`euler[1]` 只差 0.08°，但 `# yaw` 从 0.28° 突然跳到 **−32.775°**。

反推需要的角速度：`0.5 × gz × 0.005 × N = −0.576 rad`，若 `gz = −34.88`（编码下限）只需 **17ms / 3~4 帧**。
→ 判定为**收到 payload 全 0 的坏帧**，`uint_to_float(0, −34.88, 34.88, 16)` 正好解出编码下限。

```c
gz = g_att.gyro[2] - g_att.gz_bias;
if (gz > 12.0f || gz < -12.0f) {   /* 12 rad/s = 688°/s，整车不可能 */
    g_imu_rej++;
    gz = 0.0f;                      /* 当这次没数据 */
}
```

**② 在线零偏学习去掉 `NAV_IDLE` 限制**

```c
/* 改前: if (g_nav_state == NAV_IDLE && |gz−bias| < 0.03)  ... */
/* 改后: if (|gz−bias| < 0.03) ...  —— 行驶中也能收敛 */
```

原因：实测两段 500mm 直行时 yaw 以 **0.078°/s** 漂移（70 秒 5.5°），而**静止时几乎不漂**。
差别就在 `state`：静止是 `NAV_IDLE`（学习开），跑路径是 `NAV_RUN`（学习关）。
幅度门 0.03 rad/s（1.7°/s）已足以排除真实转向，所以状态限制是多余的。

> **注意一个测量陷阱**：静止测漂移时学习是开的，行驶时（改之前）是关的，**两者不可比**。
> 判断零偏好坏必须在 `state != IDLE` 时测，或者直接看 `bias z` 的绝对值。

### 10.7e ⛔ `ATT_USE_EULER` 应**永远保持 0**

实测 70 秒静止对照（同一时刻两条曲线）：

| | 起始 | 70 秒后 | 漂移率 |
|---|---|---|---|
| `euler[1]`（IMU 内部欧拉） | −0.15° | −0.55° | **−0.0057°/s** |
| `# yaw`（本工程陀螺积分） | 0.277° | 0.275° | **≈0** |

IMU 的 euler 也是纯陀螺积出来的（**无磁力计**），漂得比本工程积分还快。
所以 `ATT_USE_EULER = 0` 是正确选择，`ATT_EULER_FIELD` 那个 2 只影响死代码，**不必改**。

### 10.7f 🔴 IMU 会在大电流时掉电复位，且**不会自恢复**（2026-11-21 实测）

**故障现象**（这是本工程最危险的硬件问题，务必记住）：

```
车原地转向（wz 打满 2.5 rad/s，四轮同时最大出力）
  → yaw 从 90.00 起一动不动，连 90.01 都没有
  → 车按指令一直转，永远到不了位，state 卡在 1
```

此时敲 `i` 看到：

| 指标 | 值 | 含义 |
|---|---|---|
| `gyro` 帧数 | **持续增加** | IMU 还在回帧 |
| `last gyro frame` | `02 00 FF 7F FF 7F FF 7F` | 三轴恒为编码中点 0x7FFF = 0 |
| `gyro x/y/z` | 恒 `−0.0005 / −0.0005 / −0.0005` | 三轴**完全相同**（正常静止时各轴噪声不同） |
| `euler[0..2]` | `−0.00 / −0.00 / −0.00` | **欧拉角也归零 → IMU 复位过** |
| `tx_err` | 从 0 涨到 39（≈390ms） | 曾短暂掉线 |
| `rej` | 0 | 不是坏帧，是**真实的零** |

**手转车 90° 时 gyro 依然恒零** → 确认 IMU 已死。

**结论**：电机大电流 → 电源跌落 → IMU 掉电复位 → **卡在"输出全零"状态，只有断电才能恢复**。
`g_att.yaw` 是软件积分值，IMU 复位不会重置它，但 gyro 恒 0 → yaw 永久冻结 → 航向环死循环。

**已加的软件保护**（2026-11-21）：

| 保护 | 位置 | 行为 |
|---|---|---|
| IMU 失效检测 | `Attitude.c` | 三轴恒 0x7FFF 持续 1s，或无新帧 0.5s → `g_imu_dead=1` |
| IMU 失效停车 | `Nav.c:Nav_Update()` 开头 | `RUN/ALIGN` 态下 `g_imu_dead` → `NAV_FAIL` + 停车（手动 `v` 不受影响） |
| 转向超时 | `Nav.c` 转向分支 + ALIGN 分支 | 4s 转不到位 → `NAV_FAIL` |
| 转向限速 | `Nav.c` | 原地转向 wz 限到 **1.2 rad/s**（原来打满 2.5，电流峰值大且易打滑） |

**根因在硬件，软件只能兜底。彻底解决要做的**：

1. **IMU 单独供电**，不要和四个电机共用同一路 5V/3V3
2. IMU 电源脚并 **100µF 电解 + 0.1µF 瓷片**
3. 检查电池放电能力与线径（转向瞬间压降）
4. 可选：检测到失效后自动发 `Restart_IMU(0x00)` 或 `Set_the_angle_to_zero(0x05)`（驱动里已有 `Restart_IMU_Data_Quaternion()`），但重启后 euler 归零、绝对朝向丢失，比赛中不如直接停车判失败

### 10.8 🟡 A* 堆容量偏小

`MAP_CELLS*2` 允许重复入堆，实际峰值约 7000 > 4608，建议加 closed set。

## 11. 他的设计想法与决策理由

> 这一节是从 README「关键设计决策」和双端交流文档里提炼的**本人意图**，不是技术推断。

### 11.1 为什么机械臂拆到 F103 上

H723 要跑 480MHz 的导航/A*/四电机 CAN，实时性已经很紧。
机械臂的 50kHz 脉冲生成是硬实时，拆到独立的 F103 上互不干扰——**底盘卡了不影响机械臂脉冲，机械臂丢步不影响底盘控制**。

### 11.2 为什么 yaw 追 dx 而不是极角

见 §8.2。极角在相机坐标系下会在 ±π 跳变，实车抖到不能用。
改成两轴解耦后：**yaw 只消 x，A 轴只消 y，互不干扰**，各自调参也简单。

### 11.3 为什么范围收缩成「F103 单向控制 yaw」

原方案是双向：底盘能下发 A 轴目标、启停视觉跟随、手动/自动切换。
后来拍板收缩为「**F103 发命令 + 两边都能发状态**」，H723 本期不下命令。
**代价：F103 的视觉 PID 永久在线，没有任何外部命令能接管或关闭 A 轴。**
`g_track_enabled` 已删除。
> 如果以后要「底盘指挥机械臂」，就要改协议加命令帧——**现在改比以后改便宜**。

### 11.4 为什么障碍用「间隙判据」而不是整格膨胀

车体 275 mm，中部通道 450 mm，单边余量只有 87.5 mm。
整格膨胀 2 格会让通道变成 250 mm < 车宽 → 直接无解；膨胀 1 格又不够。
改为按真实间隙判据：**路径中心到实体障碍格的切比雪夫距离 ≥ 4 格 = 152.5 mm** 才可规划。
物料/夹取/扫码区**只自身阻挡、不参与膨胀**，否则车永远贴不到区域边缘。

### 11.5 为什么非运行态一律硬停

`NAV_IDLE / NAV_DONE / NAV_FAIL` 时直接 `Chassis_Hold(); return;`，**不做航向保持**。
否则 `s_yaw_t` 会保留上一段航向，配合 IMU 零偏漂移持续输出 `wz` → 车走完原地自转、急停停不住、**不发命令也自己动**。

### 11.6 为什么控制全在 1ms 中断里分频、A* 在主循环

A* 约 1~3 ms。放中断会打乱 200 Hz 节拍；放主循环又要防止结果被中断读到一半。
所以 A* 在主循环跑，结果**原子提交**（`__disable_irq` 只包住拷贝）。

### 11.7 当前阶段的重心

> 原话（2026-11-20）：「**我想先把直角机械臂的这个先放放，因为我觉得底盘要是写不好走不稳，机械臂写得再好也是白扯的。**」

所以现阶段优先底盘导航/稳定性，机械臂功能已基本可用（A 轴 + yaw 双闭环已跑通），**不要再主动给机械臂加功能**，除非明确要求。
