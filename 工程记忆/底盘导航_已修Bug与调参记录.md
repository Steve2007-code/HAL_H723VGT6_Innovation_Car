## 1. 🔴 `s_yaw_t` 初始航向算错 → 到点狂转（最隐蔽的坑）

**现象**（2026-11-21 实测）：

```
# WP total=3  pose=(1212,2155) yaw=-179.9
   [0] (1225,2175)      ← 这是"当前所在格心"，离车 24mm
   [1] (1205,2175)  seg=+180
   [2] (1205,285)   seg=-90
```

车原地转了 **247° 再反向转回来**，然后才开始走。每个航点都这样。

**根因**：

```c
/* s_commit() 里的原代码 */
s_yaw_t = s_seg_yaw(g_pose.x, g_pose.y, s_wpx[0], s_wpy[0]);
```

而 `s_wpx[0]` 是 `s_build_from_cells()` 填的**起始格心**，不是车的实际位置。
于是初始航向被算成"车 → 格心"的**斜角**：

```
车 (1212,2155) → 格心 (1225,2175)：atan2(20,13) = 57°
车实际朝 -180° → 误差 237° → 原地狂转
```

**更致命的是**：`Nav_Update()` 里**转向判据在前、到点判据在后**：

```c
if (fabsf(yaw_err) > NAV_TURN_GATE) { 原地转; return; }   // ← 先
...
if (d < 到达判据) { s_wp_next(); }                        // ← 后
```

航向错了就永远卡在转向分支，**转不到 25° 以内就永远不推进航点**，所以转不完。

**修法**（`s_build_from_cells` + `s_commit`）：

1. `s_px[0]/s_py[0]` 改成 `g_pose.x/y` —— 首点用**真实位姿**，不用格心
2. `s_commit` 里若首点就在脚下（≤40mm），**直接跳到第二点**，用第一段的真实方向定航向：

```c
if (s_wpn >= 2) {
    float d0x = s_wpx[0] - g_pose.x, d0y = s_wpy[0] - g_pose.y;
    if (d0x*d0x + d0y*d0y < 1600.0f) {   /* <40mm */
        s_wpi = 1;
        s_yaw_t = s_seg_yaw(s_wpx[0], s_wpy[0], s_wpx[1], s_wpy[1]);
    }
}
```

**验证**：改后 WP 打印首点变成实际坐标，每个航点只转一次 90°，跑完 15 点路线无一次异常旋转。

## 2. 🟡 `Nav_PlanToMm` 事后插 L 拐角 → 20mm 倒退段

**现象**：到点时先倒退 20mm 再拐弯，表现为"到了又退回去"。

**根因**：旧实现是"先按格心规划完，再把最后一个航点改成精确 mm，并补一个 L 拐角"：

```c
/* 旧代码 */
s_wpx[last] = x_mm;  s_wpy[last] = y_mm;
if (ax != 0 && ay != 0) {   /* 变斜段了, 补拐角 */
    c1 = (x0, y_mm);  c2 = (x_mm, y0);
    ...
}
```

若精确点在**来向的后方**，这个 L 会造出反向小段。例：

```
[1] (2275,725)  ↑上
[2] (2275,705)  ↓下   ← 20mm 倒退，逼车原地掉头 180°
[3] (2195,705)  ←左
```

**修法**：把精确终点**提前**到正交化之前，让 `s_ortho()` 自然处理：

```c
/* Nav_PlanToMm 现在 */
s_goal_x = x_mm;  s_goal_y = y_mm;  s_goal_exact = 1;
ok = s_plan_cells(r, c);
s_goal_exact = 0;
```

```c
/* s_build_from_cells 里 */
if (s_goal_exact && n > 1) {
    s_px[n-1] = (int16_t)s_goal_x;   /* 用精确 mm 取代最后一个格心 */
    s_py[n-1] = (int16_t)s_goal_y;
}
```

为支持这个，把 `Nav_PlanToCell` 拆成了内部 `s_plan_cells()` + 公开包装（包装里清 `s_goal_exact`）。

**教训**：**航点表要在生成阶段就完整，不要生成完再"打补丁"**。补丁永远不知道上游的上下文（来向、当前朝向）。

## 3. 🟡 精确终点与格心差 20mm → 碎腿

`s_ortho()` 会把"起点→精确终点"的细微偏差拆成一条 3~20mm 的小腿，多一次 90° 转向。

**修法**：新增 `s_drop_short(25.0f)`，正交化后去掉与前一点距离 < 25mm 的中间点（首尾保留）。

```c
s_ortho();
s_drop_short(25.0f);
s_merge_collinear();
```

## 4. 🟡 每个航点都白停一次

**现象**：每段之间车速降到 0 再重新加速，15 段多花 15~20 秒。

**根因**：

```c
if (d < 到达判据) {
    s_wp_next();
    Chassis_SetBodyVel(0.0f, 0.0f, wz);   /* ← 把速度清零了 */
    return;
}
```

**修法**：中间点推进时**不清零速度**，只推进航点，下一周期（5ms 后）自然按新段重算：

```c
if (d < 到达判据) {
    s_wp_next();     /* 不停车通过 */
    return;
}
```

终点不用管：`s_wp_next()` 在走完最后一点时会自己 `Chassis_Hold()`。

> 若新段需要转向，下一周期会进入转向分支把 vx/vy 清零，等于自然停车转身 —— 行为仍是安全的。

## 5. 🔴 IMU 大电流掉电 → 卡零输出（软件兜底，根因在硬件）

详细现象与诊断方法见主文档 §10.7f，这里只记结论：

- **触发**：四轮同时最大出力（原地转向）瞬间电流峰值 → 电压跌落 → IMU 复位
- **表现**：帧照常回（`gyro` 计数在涨），但三轴原始值恒为 `0x7FFF`（编码中点），欧拉角也全 0
- **后果**：`g_att.yaw` 永久冻结 → 航向环永远达不到目标 → **车无限原地转**
- **恢复**：**必须断电**，按复位键无效

**软件保护**（`Attitude.c` / `Nav.c`）：

| 保护 | 判据 | 动作 |
|---|---|---|
| IMU 失效检测 | 三轴恒 `0x7FFF` 持续 1s，或 0.5s 无新帧 | `g_imu_dead = 1`（锁存，需重启） |
| IMU 失效停车 | `RUN/ALIGN` 态下 `g_imu_dead` | 立即 `NAV_FAIL` + 停车 |
| 转向超时 | 4s 转不到位 | `NAV_FAIL`（`why=2`） |
| 转向限速 | 原地转向 wz 限幅 | 降电流峰值 + 防打滑 |

**失败原因码**（`g_nav_fail_why`，串口 `# route FAIL at N why=X`）：

```
1 = IMU 失效     2 = 转向超时     3 = A* 规划失败     4 = 起点/终点不可规划
```

**硬件上要做的**：IMU 单独供电、电源脚并 100µF + 0.1µF、检查电池放电能力。

## 6. 🟢 到点总差 7.5mm（系统性欠走）

15 个点实测误差**全部是 7.4~7.5mm，方向一律是"行进方向欠走"**：

| # | 目标 | 实到 | 误差 |
|---|---|---|---|
| 1 | 2195,705 | 2202,704 | +7.4, −1.0 |
| 5 | 1205,285 | 1205,292 | +0.2, +7.4 |
| 8 | 305,2155 | 305,2147 | 0, −7.5 |
| 13 | 2195,1205 | 2187,1205 | −7.5, −0.1 |

**根因**：`NAV_FINAL_MM = 8.0f`。车减速到剩 7.5mm、速度 0.02m/s 时正好掉进 8mm 判据 → 停车。

**修法**：`NAV_FINAL_MM` **8 → 5**（`Nav.h`）。

> 若改成 5 后出现"在 5mm 处推不动、一直蹭"，说明静摩擦太大，退回 6~7 或提高位置环 kp。

## 7. 🟢 扫码区为 50mm 横移白转 90°

`(2275,1225) → (2325,1225)` 只有 50mm，却要原地转 90°。而扫码摄像头装在车右侧，**根本不需要车头朝右**。

**修法**：末段 ≤ `NAV_SHORT_MM`(200mm) 时**锁定进入时的车头，纯平移**：

```c
if (s_wpi + 1 >= s_wpn) {
    float lx = ..., ly = ...;
    if (lx*lx + ly*ly <= NAV_SHORT_MM*NAV_SHORT_MM)
        s_yaw_t = g_pose.yaw;      /* 锁车头, 横移 */
    else
        s_yaw_t = s_seg_yaw(...);
}
```

另有 `g_force_strafe` 标志可**强制**某段横移（内置路线表里 `s_route_s[]` 逐点设置）。

> 长段不要横移：侧向长时间走麦轮打滑大，里程计会漂。

## 12. 加减速曲线（T 形）与"加速度计做惯导"的结论

### 12.1 现状：其实已经是梯形了，只是不对称

`Nav_Update()` 的段速度：

```c
vlim = sqrtf(2.0f * g_nav_a_dec * d * 0.001f);   /* 到点前按 sqrt(2*a*d) 限速 */
```

`Chassis_Update()` 的斜坡按 `g_ch_acc_v * 0.005` 逐周期加，即**恒定加速度**。
两者叠加就是标准梯形（T 形）：加速段恒 a_acc → 匀速 → 减速段恒 a_dec。

**真正的问题不是"不是 T 形"，而是**
1. **不对称**：a_acc = 1.8，a_dec = 0.8。加速猛（起步打滑多），减速软（时间长）。
2. 减速段的 a 原来写死在 `1.6f` 里（= 2×0.8），现场改不了。
3. 没有速度前馈：命令来自 `kp_pos * 位置误差 - kd_pos * 反馈速度`，
   实际速度剖面会随电池电压、地面摩擦变，**两次跑不一样 → 打滑不一样 → 终点不一样**。

### 12.2 已做：加减速度改成运行时可调

`<<D a>>` 同时设加减速，`<<D a_acc a_dec>>` 分开设。默认值仍是 1.8 / 0.8，
**不发命令则行为与改前完全一致**（零风险）。

```
<<D 1.2>>        # 加减速都 1.2, 真正对称的 T
<<D 1.5 1.5>>    # 同上
<<D 1.8 0.8>>    # 恢复旧的
```

改的文件：`Chassis.h/.c`（`g_ch_acc_v` + `Chassis_SetAccV/GetAccV`）、
`Nav.h/.c`（`g_nav_a_dec` + `Nav_SetADec/GetADec`，`vlim` 不再写死 1.6f）、
`Debug.c`（白名单 + `case 'D'` + 帮助）。编译 `Code=51732, 0 Error 0 Warning`。

**注意**：改 a 之后 `g_odom_scale` 必须重标，因为打滑量变了。

### 12.3 为什么"加速度计/四元数惯导 + 卡尔曼"在这里救不了

**决定性数字：加速度计分辨率。** 驱动里 `ACCEL_CAN_MAX = 235.2f` → **量程 ±24 g**，
int16 映射 → **1 LSB = 470.4/65535 = 0.00718 m/s² = 0.73 mg**。

二次积分下，一个恒定偏置 b 在 T 秒后造成的位移误差 `e = 0.5*b*T²`：

| 残余偏置 | T=1s | T=2s | T=4s | T=13s（跑完一圈） |
|---|---|---|---|---|
| 1 LSB = 0.73 mg | 3.6 mm | 14.4 mm | 57 mm | **608 mm** |
| 0.1 mg（ZUPT 校得很好） | 0.5 mm | 2 mm | 8 mm | 83 mm |

而编码器现在的误差是全程 9.68m 的 0.3~1% = **29~97mm**。也就是说：
**惯导最好情况（0.1mg）也就和编码器打平，正常情况差 6 倍。**

**更致命的是重力泄漏。** 车放平后 IMU 仍可能有 1° 安装倾角：

```
9.8 * sin(1°) = 0.171 m/s² = 24 LSB 的直流偏置
→ 4 秒后位移误差 0.5 * 0.171 * 16 = 1.37 米
```

要积分，倾角必须扣到 0.01° 以内（MEMS 做不到）。
**这正是"四元数"在这里的地位**：四元数唯一的作用是把重力从三轴比力里投影掉，
而它的精度要求恰好是这个方案达不到的那一关。所以四元数不是解法，是死因。

**还有架构上的坎**：IMU 是**被动轮询**的，一次请求只回一个寄存器
（`Red_DM_IMU_GyroData()` 在 5ms 里发一次）。寄存器 `0x0F`（输出数据选择）
手册明确写**当前固件不支持修改** → 主动上报模式拿不到加速度。
要用加速度就得在 5ms 时隙里再塞一对请求/应答（现有代码在 10ms 里已经这么干过
Euler+Gyro，所以技术可行），但 CAN 流量翻倍、`tx_err` 风险变大。

### 12.4 结论：加速度计值得用，但不是用来积分

| 方案 | 判断 |
|---|---|
| 加速度二次积分算距离 | ❌ 分辨率 + 重力泄漏，物理上不可能 |
| 加速度 + 编码器做 8 状态卡尔曼 | ⚠️ 能做，但两路误差量级相同、且编码器误差是**相关**的（比例误差），KF 会基本跟着编码器走，收益 < 复杂度 |
| **加速度做"打滑门控"（不积分）** | ✅ 推荐。不需要 KF，不需要积分，阈值裕度极大 |
| 陀螺仪/四元数管航向 | ✅ 已经在用，实测全圈 0.23°，够好 |

**打滑门控原理**：正常时 `a_enc = d(fb_vx)/dt` 和 IMU 测到的 `a_imu` 应该相等；
轮子空转时 `a_enc` 明显大于 `a_imu`。判据

```
若 (加速段中) 且 (a_enc - a_imu > 0.15 m/s²) 连续 20ms
  → 判定打滑, 该周期里程计增量 ×0.6 或直接冻结
```

0.15 m/s² 的阈值对 0.0072 m/s² 的分辨率来说是 20 倍裕度，非常稳。
它只打**加减速那 0.4~0.9 秒**，正好是目前剩下误差的第二大来源。

**免费的替代品**：同一件事可以先用陀螺仪做——直线段上如果出现没被命令的 yaw 瞬态，
说明某个对角轮先失去抓地（麦轮打滑几乎总是不对称的）。这个不用加任何硬件和请求。

### 12.5 唯一能把误差"清零"的路

纯轮速里程计跑 9.68m、过 10 次转，现实下限就是 **15~30mm**，
不可能到 5mm——因为没有绝对参考，误差只会累积不会被拉回。
要清零只能靠：地面色块边界（朝下相机）、二维码板/夹取台的物理触碰（加一个碰撞开关）。
规则不允许贴标记，但**场地本身的地面涂装是允许被拍的**。

## 13. 🔴 转向后「还在转就起步」→ 整圈物理偏差 115mm（2026-11-21 夜，已修）

**现象**：单腿直线全部零误差（+x 2050mm→3mm、−y 1050mm→0mm、−y 200mm→0mm），
但跑完整圈 R1，车心物理漂移 **(−35, −110) mm**；而里程计每轮都稳稳报 `(2225,180)`。

**排查链路（都被数据排除掉的）**：
| 怀疑项 | 实测 | 结论 |
|---|---|---|
| 直行比例 | 2050mm 走 2050mm | ✅ 已标定 0.9755 |
| y 方向里程计 | 1050mm→1050mm | ✅ 无盲区 |
| A* 路径不确定 | 三遍航点表逐位相同 | ✅ 排除 |
| 转向角度 | 全圈 0.1° | ✅ |
| 静止原地转的平移 | 810° 车心只跑 9mm | ✅ 但**工况不对** |

**真正根因**：`Nav_Update()` 的拐点判据只看角度，
`|yaw_err|<1°` 且 `|yaw_rate|<0.08rad/s` 一满足就**立刻**开始平移。
此时底盘内部斜坡 `cwz` 还在衰减、电机还没停稳 →
**边转边走**，麦轮辊子侧向刮地。
这段车体侧滑在里程计里**完全看不见**（`fb_vx/fb_vy` 只反映轮子转速）。

**修法**：加「停稳驻留」三相位状态机。

```c
/* s_turn_phase: 0=需要对准  1=停稳驻留  2=已放行(之后连续平移) */
if (s_turn_phase != 0 && fabsf(yaw_err) > NAV_TURN_GATE)
    s_turn_phase = 0;                  /* 平移中跑偏过大 -> 重新停下对准 */

if (s_turn_phase == 0) { ...原转向逻辑... -> 到位后 phase=1, 开始计时 }
if (s_turn_phase == 1)
{
    if (|fb_vx|>NAV_SETTLE_V || |fb_vy|>NAV_SETTLE_V || |fb_wz|>NAV_SETTLE_WZ)
        s_settle_ms = Tick;            /* 还在动: 重新计时 */
    Chassis_SetBodyVel(0,0,0);
    if (驻留未够 && 未超时) return;
    s_turn_phase = 2;                  /* 放行 */
}
```

参数：`g_nav_settle_ms` 默认 **200ms**，`<<S ms>>` 现场调（0~800）；
`NAV_SETTLE_V=0.015 m/s`、`NAV_SETTLE_WZ=0.03 rad/s`；
最长兜底 `settle+600ms`，保证不会卡死。
清零点：`s_wp_next()` / `s_commit()` / 退出运行态。

**效果**：用户实测「飘得没那么离谱了，基本回到出发点」。

**中间踩的坑（务必记住）**：第一版用布尔量 `s_turn_settled`，驻留结束时清 0，
下一周期 `!s_turn_settled` 又从头进入驻留 → **每 120ms 只有 5ms 在平移（4% 占空比）**，
现象是「发了 `<<R 1>>` 车完全不走」。带等待的状态机必须用显式相位，不能用布尔。

**代价**：每航点多 200ms，R1（16 航点）约 +3.2s。

## 14. 起点 x 方向 25mm 系统偏差（待修）

`Nav_ResetPose(44,44)` → col44 格心 **(2225,175)**；
但启停区 = rows42~47 × cols42~47 = x 2100..2400 → 几何中心 **(2250,175)**。

车 290×270 放进 300×300 启停区，x 向只有 ±5mm 余量 → **车必须摆在 2250**。
而规划器边界规则 `MAP_BORDER_CELLS=3` 只允许 col ≤44（x≤2225），差 25mm。

后果：功能区点物理上整体偏右 25mm（回原点不受影响，因为是常量）。
修法：起点改 `Nav_SetPoseMm(2250,175,90)` + P5 改 (2250,175)，代价是 leg1 多 25mm 横向修正。
